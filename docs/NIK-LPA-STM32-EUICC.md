# NIK LPA STM32 / eUICC integration

## Scope

This document defines what a meter firmware based on STM32 must implement in order to replace the Windows Card Agent side of NIK LPA.

Transport between the meter and the external Server Agent is deliberately out of scope. The meter is treated as a Card Agent appliance: it owns access to the eUICC and executes ES10b operations requested by the external side.

The STM32 does not need to implement the Server Agent, ES9+, HTTPS, TLS, SM-DP+ discovery, activation-code parsing or profile-package generation.

## Target architecture

```text
External Server Agent
    |
    | transport is separate / unspecified here
    v
STM32 firmware
    |
    +-- NIK Card Agent command API
    |
    +-- RSP/Card Agent state machine
    |
    +-- ES10b subset
    |
    +-- eUICC HAL
            |
            +-- direct ISO7816/UICC interface
            |
            `-- modem APDU tunnel
                    |
                    v
                  eUICC
```

The most important abstraction is a raw APDU transceive interface. Everything above it should be independent of whether the physical card is wired directly to STM32 or belongs to the modem.

## Required Card Agent operations

Minimum API:

```c
int euicc_open(void);
int euicc_reset(uint8_t *atr, size_t *atr_len);
int euicc_transmit_apdu(const uint8_t *tx, size_t tx_len,
                        uint8_t *rx, size_t *rx_len);
int euicc_close(void);

int rsp_read_eid(...);
int rsp_init(...);
int rsp_authenticate_server(...);
int rsp_prepare_download(...);
int rsp_install_bpp_begin(size_t total_length);
int rsp_install_bpp_write(const uint8_t *data, size_t length);
int rsp_install_bpp_finish(...);
int rsp_get_profiles(...);
int rsp_cancel(...);
```

The exact external serialization is not defined here; these operations are the firmware-domain contract.

## Required state machine

```text
IDLE
  |
  | read EID / rsp_init
  v
INIT_READY
  |
  | AuthenticateServer
  v
AUTHENTICATED
  |
  | PrepareDownload
  v
PREPARED
  |
  | Begin/stream/finalize BPP
  v
INSTALLING
  |
  | LoadBoundProfilePackage success
  v
VERIFYING
  |
  | fresh Profile List contains expected ICCID
  v
INSTALLED
```

Any active state must support cancellation/recovery where the eUICC transaction allows it.

Invalid ordering must be rejected. For example, `LoadBoundProfilePackage` must not be accepted directly from `IDLE`.

## Operation details

### Read EID

Purpose: identify the physical eUICC.

Firmware requirement:

- open/reset the card path;
- select/access the required eUICC application/domain through the ES10b/libeuicc-equivalent stack;
- read the EID;
- expose the EID to the application layer or expose a hash if product privacy policy requires it.

NIK desktop currently hashes the EID with SHA-256 for the relay packet target identifier.

### `rsp_init`

Equivalent desktop functions:

```text
es10b_get_euicc_challenge_r
es10b_get_euicc_info_r
```

Input:

```text
none, except active eUICC session
```

Card operations:

```text
GetEuiccChallenge
GetEuiccInfo1
```

Output:

```text
euiccChallenge
euiccInfo1
```

The challenge is fresh data generated by the eUICC for the authentication flow. `EUICCInfo1` describes eUICC/RSP capabilities needed by the SM-DP+ side.

### `rsp_authenticate_server`

Input received from the Server Agent:

```text
serverSigned1
serverSignature1
euiccCiPKIdToBeUsed
serverCertificate
matchingId
optional IMEI
```

Equivalent desktop call:

```text
es10b_authenticate_server_r
```

The firmware/ES10b stack sends the corresponding AuthenticateServer material to the eUICC. The eUICC performs protocol-level certificate/signature validation and creates the response.

Output:

```text
authenticateServerResponse
transaction ID bytes/state needed for later cancellation
```

The firmware should preserve the active card-side transaction state until completion or cancellation.

### `rsp_prepare_download`

Input received from the Server Agent:

```text
profileMetadata
smdpSigned2
smdpSignature2
smdpCertificate
optional confirmationCode
```

Equivalent desktop call:

```text
es10b_prepare_download_r
```

Output:

```text
prepareDownloadResponse
```

The output is treated as opaque RSP protocol data by the external transport/application layer.

### `rsp_install_bpp_*`

Input:

```text
BoundProfilePackage
```

Equivalent desktop call:

```text
es10b_load_bound_profile_package_r
```

On a desktop implementation the BPP can be represented as a large string/buffer. On STM32 this should not be the default design.

Use a streaming API:

```text
rsp_install_bpp_begin(total_length)
  -> rsp_install_bpp_write(chunk)
  -> rsp_install_bpp_write(chunk)
  -> ...
  -> rsp_install_bpp_finish()
```

The firmware should feed chunks to the ES10b/BPP parser/loader and APDU transfer path without requiring the full profile package in RAM.

Expected result information:

```text
sequenceNumber
ICCID
bppCommandId
errorReason
```

The exact parser implementation can reuse/port the smallest practical subset of `libeuicc` rather than rewriting ASN.1/RSP logic from scratch.

### Profile List verification

After `LoadBoundProfilePackage` reports success, perform a fresh profile-list operation.

Validation rule:

```text
expected ICCID returned by LoadBoundProfilePackage
    must exist in fresh Profile List
```

Only then report installation success to the external Server Agent.

### Cancel

The firmware should preserve enough active transaction state to execute the ES10b CancelSession path when required.

Typical reasons:

- operator rejection;
- malformed/invalid incoming stage;
- server-side failure;
- BPP failure;
- session timeout;
- explicit abort.

## APDU HAL

Recommended abstraction:

```c
typedef struct {
    int (*open)(void *ctx);
    int (*reset)(void *ctx, uint8_t *atr, size_t *atr_len);
    int (*transmit)(void *ctx,
                    const uint8_t *command, size_t command_len,
                    uint8_t *response, size_t *response_len);
    int (*close)(void *ctx);
    void *ctx;
} euicc_transport_t;
```

Two implementations can then exist without touching ES10b logic:

```text
euicc_transport_iso7816.c
euicc_transport_modem.c
```

## Physical UICC/eUICC contacts

A traditional removable SIM/UICC contact set is commonly described as follows:

| Contact | Conventional name | Function | Meter relevance |
|---|---|---|---|
| C1 | VCC | UICC supply | required if STM32 directly powers the eUICC |
| C2 | RST | reset | required for direct host control |
| C3 | CLK | clock supplied by terminal | required for direct ISO7816/UICC host |
| C4 | reserved / AUX | historically reserved or optional interface depending on card/application | normally not needed for basic eUICC APDU access |
| C5 | GND | ground | required |
| C6 | VPP | legacy programming voltage; generally not used by modern UICC | normally leave according to hardware/datasheet requirements |
| C7 | I/O | half-duplex serial data | required |
| C8 | reserved / AUX | optional/reserved depending on implementation | normally not needed for basic APDU access |

For soldered eUICC packages, the package pin names and number of pins vary by manufacturer. Do not copy the removable SIM C1-C8 numbering directly onto a specific MFF2/WLCSP/BGA footprint without the exact eUICC datasheet and schematic.

### Signals that actually matter for basic direct card access

At logical UICC level the essential host signals are:

```text
VCC
GND
CLK
RST
I/O
```

Potential board-level additions may include:

```text
power-enable/load-switch control
card/eUICC presence indication
level translator enable
ESD protection
SIM mux select
modem/MCU ownership select
```

These additions are board-specific, not universal eUICC protocol pins.

## Electrical caution

Do not assume STM32 GPIO voltage equals eUICC I/O voltage.

The actual product must verify from the modem/eUICC datasheets and schematic:

- supported UICC supply classes/voltage;
- I/O electrical levels;
- clock requirements;
- reset timing;
- whether a SIM level translator is already present;
- whether power is generated by the modem;
- whether signal ownership is multiplexed.

Do not directly drive a modem-owned SIM bus from STM32 unless hardware explicitly provides a safe mux/arbitration mechanism.

## Hardware topology A: eUICC directly owned by STM32

```text
STM32                    eUICC
-----                    -----
UICC_VCC  -------------- VCC
UICC_GND  -------------- GND
UICC_CLK  -------------- CLK
UICC_RST  -------------- RST
UICC_IO   <------------> I/O
```

Required firmware responsibility:

- UICC electrical initialization;
- ISO7816/UICC timing/protocol;
- ATR handling;
- APDU command/response handling;
- logical-channel/application selection as required;
- recovery/reset.

This gives maximum control but also makes the STM32 responsible for the low-level smart-card host implementation.

## Hardware topology B: eUICC owned by modem

This is often the preferable meter architecture when the modem already has a UICC/SIM interface.

```text
STM32
  |
  | UART / USB / other modem control interface
  v
MODEM
  |
  | SIM_VCC / SIM_CLK / SIM_RST / SIM_IO
  v
eUICC
```

STM32 then requires a modem API that exposes raw smart-card access. Typical categories are:

```text
open logical channel
close logical channel
send APDU on basic/logical channel
receive APDU response
```

Many cellular modem command sets expose generic UICC APDU commands derived from 3GPP AT-command concepts such as `+CSIM` and/or logical-channel commands such as `+CGLA`, but exact command availability and restrictions are modem-vendor/model specific.

The correct implementation is therefore:

```c
static int modem_euicc_transmit(...) {
    // map raw APDU request to the modem's documented UICC/APDU command
    // collect response bytes and return them unchanged to ES10b layer
}
```

The ES10b code above this function remains unchanged.

## Hardware topology C: modem with integrated eUICC/LPA functionality

Some modem modules expose a high-level eSIM manager rather than unrestricted raw APDU access.

If the modem only supports a command conceptually equivalent to:

```text
download profile using complete activation code
```

then the modem is trying to own both ES9+ and ES10b and is not a drop-in replacement for the staged NIK Card Agent.

For the current staged architecture, prefer one of these capabilities:

1. direct raw eUICC access from STM32; or
2. modem-controlled eUICC with raw/basic/logical-channel APDU tunnelling.

## What to inspect on the meter schematic

Before firmware implementation, determine the actual ownership of the eUICC bus.

Search schematic/BOM/net names for items such as:

```text
SIM_VCC
VSIM
SIM_CLK
SIM_RST
SIM_IO
UIM_VCC
UIM_CLK
UIM_RESET
UIM_DATA
USIM
eSIM
eUICC
SIM_MUX
SIM_SEL
```

Then trace those nets to answer:

1. Which IC supplies eUICC VCC?
2. Which IC drives CLK?
3. Which IC drives RST?
4. Where does bidirectional I/O terminate?
5. Is there a level translator?
6. Is there a SIM/eSIM mux?
7. Can STM32 obtain exclusive ownership?
8. Is eUICC an external package or integrated into the modem/module?
9. Does the modem expose raw APDU access in its command set?

## What information is still required for exact pin-level implementation

The generic UICC contact list above is sufficient for architecture, but exact meter firmware/pin assignment cannot be written until the project provides:

```text
STM32 exact part number
modem exact part number
eUICC exact part number/package
meter schematic or relevant SIM/eSIM pages
board net names and MCU/modem pin assignments
```

Without those inputs, assigning a concrete GPIO such as `PA9`, `PB6` or a modem pin number would be fabrication rather than engineering.

## Memory and robustness requirements

Recommended constraints for MCU implementation:

- avoid full-BPP buffering in RAM;
- use bounded buffers for ASN.1/APDU processing;
- support APDU response chaining as required by the selected stack/card;
- zero sensitive temporary buffers after use where practical;
- preserve only the minimum RSP session state needed between stages;
- define explicit timeout/recovery behavior;
- make session reset idempotent;
- reject stage replay or invalid state transitions;
- separate transport framing from RSP/Card Agent logic.

## Compatibility target

The first embedded milestone should be behavioral compatibility with the current Windows Card Agent:

```text
Read EID
GetEuiccChallenge + GetEuiccInfo1
AuthenticateServer
PrepareDownload
LoadBoundProfilePackage
fresh Profile List / ICCID verification
CancelSession
```

Once those operations work against the same test eUICC and the same Server Agent, the STM32 side can replace the desktop Card Agent regardless of the final meter-to-server transport.
